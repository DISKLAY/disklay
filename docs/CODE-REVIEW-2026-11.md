# Medzo: оценка кода и инфраструктуры (16.11.2026)

Что проверено: клиент (`js/`, ~61k строк, 32 скрипта в `index.html`), CSS (3.2k строк), 364 теста
(`node --test tests/*.test.js` — все проходят, ~11 с), миграции и Edge Functions в `supabase/`,
а также состояние живого проекта Supabase `pgkimwwxoxizlmncdevq` (таблицы, RLS, функции,
секреты, нагрузка из `pg_stat_statements`).

Общая оценка: **архитектура продуманная, гигиена безопасности выше среднего для статического
учебного приложения**. Основные потери — не в «грязном коде», а в **весе старта, дублировании
между разделами и в нескольких местах, где описание расходится с фактическим поведением**.

Итоговые оценки:

| Область | Оценка | Комментарий |
|---|---|---|
| Данные и ключи | 9/10 | 2174 вопроса, восстановленные ключи, пометки о расхождениях, честные дисклеймеры |

| Документация | 7/10 | README подробный, но местами противоречит коду и тексту бота |

## 1. Что сделано действительно хорошо

- **Данные.** 11 баз, 2174 вопроса, отдельные файлы ключей, предупреждения по конкретным номерам
  (`questionWarnings` в `js/modules.js`) и честная формулировка «официальный ключ не сверялся».
  Это сильнее, чем у большинства студенческих тренажёров.
- **Серверная модель доверия.** Клиент никогда не ходит в PostgREST напрямую: все операции идут
  через Edge Functions с `service_role`, а RLS на всех 12 таблицах включён и `anon`/`authenticated`
  отозваны везде (0 политик — это правильно, потому что доступа нет вообще). SECURITY DEFINER
  функции имеют `search_path=''` и `revoke all … from public, anon, authenticated`.
- **Сессии.** Случайный `sid` (32 байта) хранится в БД только как SHA-256; подпись HMAC на секрете
  бота; `/logout` отзывает сессию на сервере; «Запомнить меня» честно разделяет `localStorage`
  и `sessionStorage`.
- **Конкурентность синхронизации.** Optimistic concurrency по `revision` под `select … for update`,
  защита от «отката» schema-2 → schema-1, история из 10 ревизий, локальная резервная копия перед
  любой заменой, `Web Locks` для мультивкладочности. `study-sync-engine.js` — маленький и честный.
- **Приватность.** Telegram ID никогда не покидает сервер, рейтинг — по явному согласию,
  фото 160×160 JPEG с удалением EXIF через canvas, лимиты на размер/base64/MIME.
- **Пароли.** Отдельная схема: логин → случайный внутренний UUID, пароль живёт только в Supabase
  Auth, rate limit по логину и глобально, регистрация через «резервирование» логина.
- **Доступность.** `skip-link`, `aria-live` для результатов, `prefers-reduced-motion` в основных
  файлах, `focus-visible` стили, `lang="ru"`, осмысленные `alt`/`aria-label`, тач-таргеты ≥42 px.
- **Честные тесты.** 364 теста, включая серверные (`study-sync-server`, `medzo-credentials-*`) на
  подставных адаптерах, а не только «smoke».

## 2. Находки, которые стоит исправить в первую очередь

### P0 — описание расходится с поведением

1. **README обещает «работу офлайн», но сервис-воркера нет.**
   `grep serviceWorker` по репозиторию — 0 совпадений, `manifest.json` тоже нет.
   Офлайн работает только за счёт кэша браузера, то есть после «Clear site data» сайт не откроется.
   *Действие:* либо добавить SW с версионированным precache (см. §3.6), либо переписать строку 46
   README на «работает без интернета после первой загрузки (кэш браузера)».

2. **Текст бота противоречит фактической синхронизации.**
   В `medzo-bot/index.js` (`WELCOME`) написано: «Игра, кошелёк и оформления не синхронизируются»,
   а README (§ «Очки, достижения и оформления») и код (`study-snapshot.js`, `rewardFields`,
   `sharedKey`) синхронизируют кошелёк, достижения и оформления. Не синхронизируется подземелье.
   *Действие:* поправить текст в боте (он уходит пользователю первым).

3. **`deploy-loader.js` тянет бандл с GitHub через `(0,eval)(code)` при каждом холодном старте.**
   Хэш сверяется (я проверил: локальный `bundle.js`, коммит `bae313b` и продовая функция дают
   одинаковые SHA-256 `6a06268…4202a`), но при недоступности `raw.githubusercontent.com` парольный
   вход целиком умирает, а `eval` произвольного кода — плохой паттерн даже с проверкой хеша.
   В README это описано, но это остаётся единственной точкой отказа, которой нет у Telegram-входа.
   *Действие:* залить собранный `bundle.js` прямо в тело функции (`update_edge_function` c `body`).

4. **Миграции в репозитории и в базе не совпадают по версиям.**
   В репозитории: `20261106190000`, `20261107000000`, `20261107100000`, `20261107110000`,
   `20261107120000`, `20261107140000`, `20261114100000`.
   В базе: `20261106203309`, `20261107082945`, `20261107084422`, `20261107084718`, `20261107092120`,
   `20261107182911`, `20261114222231`.
   Схема при этом совпадает (я сверил все 9 функций и индексы), но «накатить репозиторий на чистую
   БД» и «понять, что реально применено» сейчас нельзя.
   *Действие:* переименовать файлы под версии из `list_migrations` (или наоборот — зафиксировать
   приоритет репозитория и накатить `supabase db push`).

### P1 — безопасность и устойчивость

5. **Модальное окно подтверждения закрывается по `Enter` из любого места документа.**
   `js/ui.js:191` — `document.addEventListener('keydown', onKey)` без проверки цели. Enter,
   нажатый в любом поле ввода или на кнопке под модалкой, нажимает «подтвердить».
   Для диалогов «Сбросить прогресс?» и «Купить оформление за 5000?» это опасно.
   *Действие:* обрабатывать `Enter` только если `e.target` внутри `wrap` и это не `textarea`;
   заодно добавить focus-trap (сейчас его нет) и возврат фокуса на кнопку-инициатор.

6. **Прод Supabase живёт с дефолтным конфигом Auth.**
   `site_url = http://localhost:3000`, `uri_allow_list = ""`, `password_min_length = 6`,
   `password_hibp_enabled = false`, `security_update_password_require_current_password = false`,
   `sessions_single_per_user = false`.
   Приложение требует от 10 символов, но это проверка только на клиенте/в адаптере — сам Supabase
   примет 6. Пока парольные аккаунты помечены «экспериментальными», это терпимо, но при выпуске
   «Восстановления пароля» дефолтный `site_url` станет реальной дырой (редирект на localhost).
   *Действие:* `site_url=https://disklay.github.io/disklay/`, `uri_allow_list` тем же значением,
   `password_min_length=10`, `password_hibp_enabled=true`, выключить `external_email_enabled=false`
   (email-регистрация не используется: аккаунты создаются через admin API).

7. **Счётчики `medzo_password_attempts` и просроченные сессии чистятся только «по случаю».**
   Сессии: `expires_at` проверяется при каждом запросе, но `delete` для просроченных нигде нет
   (сейчас 0 просроченных из 16 — но это пока). Nonce чистятся, attempts — при следующей попытке.
   *Действие:* `pg_cron`-джоба раз в сутки: `delete from medzo_study_sessions where expires_at < now()`
   и то же для `medzo_study_login_nonces`.

8. **`medzo_study_sync_put` может «застрять» на конфликте.**
   Если в базе уже schema-2, а клиент schema-1 (старый браузер), функция возвращает `conflict` с тем
   же `revision` — клиент будет повторять попытку и никогда не продвинется. Сейчас это редкий случай,
   но при откате версии сайта он превращается в «синхронизация не работает и непонятно почему».
   *Действие:* отдавать отдельный код ошибки (`schema_conflict`), который клиент показывает как
   «обновите страницу/приложение».

9. **Leaderboard отдаёт фото в base64 внутри JSON, до 100 записей одним ответом.**
   При 8 КБ на аватар ответ ~0.8 МБ, при 40 КБ — ~3.9 МБ. Плюс `display_name` не фильтруется от
   управляющих символов, кроме C0/C1 — RTL-override и zero-width проходят и ломают вёрстку списка.
   *Действие:* отдавать `photo_url` из Storage (или хотя бы `limit 25` по умолчанию + отдельный
   запрос за фото при раскрытии), фильтровать `\p{Cf}` и bidi-контролы в имени.

10. **Дублирование проверки сессии между функциями.**
    `medzo-oral-sync`, `medzo-myology-sync`, `medzo-study-sync`, `medzo-credentials` содержат четыре
    копии `hmac/equal/unb64/signObject/verifyObject` (у oral и myology — 86 % строк идентичны,
    `validSnapshot` объявлен в трёх местах). Это уже привело к расхождению: в `study-sync` есть
    проверка `typeof session.sid`, в oral/myology — своя, чуть другая логика.
    *Действие:* один модуль `supabase/functions/_shared/session.js` и импорт
    `import { verifySession } from '../_shared/session.js'` в каждой функции (Edge Functions это
    поддерживают; `medzo-credentials` уже собирается скриптом, остальные можно перевести так же).

### P2 — производительность

11. **Стартовый вес: 1.63 МБ JS (269 КБ gzip) до первого экрана.**
    На главной `index.html` подключает данные **всех 11 баз** (1.35 МБ `js/data/*.js`, из них
    195 КБ gzip), хотя после загрузки используется ровно одна. Если грузить только выбранную базу,
    экономия ~177 КБ gzip и ~1.1 МБ несжатого — это 60–70 % стартового трафика данных.
    *Действие:* оставить в `index.html` только `questions.js + answers.js + exam.js`, а
    `js/data/<base>.js` подгружать динамически при переключении базы (в `moduleSelect.change`
    уже есть `location.reload()` — туда и вставляется догрузка).

12. **Переключение базы — это `location.reload()`** (`js/app.js:384`). Пользователь ждёт полную
    перезагрузку 1.6 МБ. После п.11 перезагрузка останется, но станет дешёвой; в идеале —
    пересоздание `AT` без релоада.

13. **27 `?v=`-строк поддерживаются руками, 8 скриптов вообще без версии**
    (`questions.js`, `exam.js`, `colloquium-2/3/4`, `credit-2`, `dental-2/3`). Это уже
    «дамоклов меч»: правка `modules.js` требует вспомнить про `?v=`, иначе часть пользователей
    останется на старом файле. И наоборот — версия зашита как дата, но не связана с содержимым.
    *Действие:* при переходе на минимальный шаг сборки — хэш содержимого в имени файла
    (`questions.a1b2c3.js`). Без сборки — хотя бы один общий `BUILD_ID` в `index.html`.

14. **Тяжёлые GIF (15 МБ) и `germ-squad.js` в горячем пути.**
    `rick-morty-intro-hd.gif` 7.5 МБ, `breaking-bad-intro.gif` 2.9 МБ, `titan-intro.gif` 2.4 МБ,
    `patriotic-baikal.gif` 2.4 МБ. Они грузятся только при выборе соответствующего оформления
    (это правильно), но 7.5 МБ GIF — это секунды на мобильном интернете. `germ-squad.js` (12.7 КБ)
    подключается в `index.html` для пасхалки.
    *Действие:* перекодировать интро в `<video autoplay muted playsinline>` с WebM/H.264 или
    в постер + короткий WebP-фрагмент (7.5 МБ → ~300–500 КБ). `germ-squad.js` — лениво.

15. **`anatomy-oral-source.js` — 398 595 символов в одной строке**, `myology-data.js` — 140 374.
    Это не влияет на браузер, но ломает diff’ы, code review и подсветку в редакторе.
    *Действие:* `JSON.stringify(obj, null, 1)` при генерации — файл вырастет в 1.5–2 раза, но
    останется сжимаемым; лучше — вынести в `.json` и грузить `fetch`ом (тогда и кэшируется браузером).

16. **CSS 129 КБ (25 КБ gzip) одним файлом, из них заметная часть — оформления.**
    `styles.css` содержит все темы (океан/гранат/янтарь/3 сезона/3 «особых»), разметку подземелья и
    пасхалок. На главной нужна малая часть.
    *Действие:* разнести на `base.css` + `themes.css` (подключать `themes.css` только при
    не-дефолтном оформлении) — минус ~20 КБ gzip на первой загрузке.

17. **Нет `defer` на 32 скриптах.** Все `<script>` в конце `<body>`, поэтому парсинг не блокируется,
    но `defer` дал бы параллельную загрузку + строгий порядок без блокировки DOMContentLoaded.
    Тривиально и бесплатно.

### P2 — качество кода

18. **`js/study-sync.js` — 526 строк, из которых 90 % логики лежат в 8-строчных строках.**
    Файл управляет четырьмя независимыми синхронизациями (учебной, устной, миологической,
    рейтингом) и фото, при этом `oralEngine`/`myoEngine` копируют друг друга почти дословно.
    *Действие:* вынести `createSecondarySync({endpoint, snapshot, metaKey, ownerKey, label})`
    — уберёт ~150 строк дублей и три одинаковых `catch`-блока.

19. **Дубли подходов к хранилищу.** `oral-snapshot.js` и `myology-snapshot.js` — один и тот же
    паттерн (`validate/capture/apply` + резервная копия), а `study-snapshot.js` — третий вариант
    с теми же идеями. Локальные backup-ключи (`medzo-*-sync-local-backup-*`) **никогда не удаляются**
    — при частых pull’ах они копятся в `localStorage` и могут привести к `QuotaExceededError`,
    которую никто не ловит (в `core.js:202` только `console.warn`).
    *Действие:* общий `createSnapshotEngine`, хранить не более 1–2 бэкапов на раздел (остальные
    удалять по FIFO), на quota — показать тост «не удалось сохранить, освободите место».

20. **Рендер через конкатенацию строк в `innerHTML` (28 мест) с `esc()` в 146 местах.**
    XSS закрыт (проверил: заметки, комментарии, `display_name` из рейтинга, введённый текст
    гистологии — всё через `esc`), но такой код легко «потерять» при следующей правке:
    один пропущенный `esc` — и дыра. Плюс `innerHTML` уничтожает состояние фокуса и
    пересоздаёт DOM целиком.
    *Действие:* хотя бы линтер-правило «нет `… + variable + …` внутри шаблона без `esc`» для
    `js/views-*.js`; в идеале — маленький `h()`-хелпер или `<template>`.

21. **Порядок входа в страницу: тема применяется после полной загрузки.**
    `ui.applyTheme()` вызывается в `app.js` (последний скрипт), а `index.html` жёстко задаёт
    `data-theme="light"`. Пользователь с тёмной темой видит вспышку светлого фона на каждом старте.
    *Действие:* 6-строчный инлайн-скрипт в `<head>` (или `<script>` с `defer` до стилей),
    читающий `localStorage` и ставящий `data-theme` до первой отрисовки.
    Инлайн-скрипт потребует `'unsafe-inline'`/хэш в CSP — но CSP у вас всё равно пока нет.

22. **Нет CSP.** Приложение идеально подходит под строгую политику: 0 инлайн-скриптов, 0 инлайн-стилей
    в HTML, 0 `eval` (кроме серверного `deploy-loader`), внешний код только `telegram.org` и Supabase.
    *Действие:* `<meta http-equiv="Content-Security-Policy" content="default-src 'self';
    connect-src 'self' https://pgkimwwxoxizlmncdevq.supabase.co; img-src 'self' data: blob:;
    script-src 'self' https://telegram.org; style-src 'self'">`. Учесть два ограничения:
    `frame-ancestors` в `<meta>` игнорируется браузером (нужен HTTP-заголовок, то есть прокси),
    а инлайн-скрипт для темы из п.21 потребует `'unsafe-inline'` либо хэша в `script-src`.

23. **`views-pages.js` 789 строк и `views-study.js` 1163 строки с логикой, разметкой и обработчиками
    вперемешку** — самое дорогое место для правок. `course-drawer.js`, `module-picker.js`,
    `onboarding.js` — маленькие и хорошие; стоит тянуть остальные к тому же стилю.

24. **`console.warn` вместо пользовательского сообщения при ошибке записи.**
    `core.js:202` — если `localStorage` переполнен (реально при 60 сессиях × 11 баз + бэкапы),
    пользователь не узнает, что прогресс не сохранён. `histology.js` уже умеет
    (`storageFailed()` + баннер) — надо так же в анатомии.

## 3. Предложения по улучшению (по убыванию отношения «эффект / трудозатраты»)

### 3.1 Быстрые победы (полдня)

1. Поправить текст бота (п.2) — одна строка, но это первое, что видит новый пользователь.
2. `site_url`/`uri_allow_list`/`password_min_length`/`hibp` в Supabase Auth (п.6) — 4 поля.
3. `defer` на все `<script>` (п.17) + `?v=` для 8 файлов без версии.
4. Инлайн-применение темы до отрисовки (п.21) — убирает вспышку светлой темы.
5. `Enter` в модалке — только внутри диалога (п.5).
6. README про офлайн-режим — переформулировать под реальность (п.1).

### 3.2 Один-два дня

7. **Ленивая загрузка баз**: 8 файлов данных из `index.html` → динамический `loadBase(id)`.
   Ожидаемо: −177 КБ gzip на первой загрузке, −1.1 МБ несжатого трафика.
8. **Ленивый `germ-squad.js`** и постер вместо 7.5 МБ GIF (п.14).
9. **Общий `_shared/session.js`** для Edge Functions + перенос oral/myology на него (п.10).
10. **`pg_cron` чистка сессий и nonce** (п.7).
11. **Ограничить бэкапы в `localStorage`** и обработать `QuotaExceeded` (п.19, п.24).

### 3.3 На неделю

12. **Service Worker** с precache «оболочки» (HTML+CSS+ядро JS) и stale-while-revalidate для
    данных баз. Тогда README про офлайн станет правдой, а первая загрузка не будет требовать
    сети при повторном визите. Важно: версионировать кэш по `BUILD_ID` и не кэшировать
    `/functions/v1/*` (иначе синхронизация будет «залипать»).
13. **Сборка без фреймворка**: esbuild в один `bundle.js` + хэш в имени + `content-hash` для CSS.
    Это решает и `?v=` руками (п.13), и в 2–3 раза сокращает число запросов (32 → 1–2),
    практически не меняя код (ESM-импорты вместо глобалов `window.AT` — постепенно).
14. **CI на GitHub Actions**: `node --test`, `node --check` по всем `js/**`, проверка
    «нет файлов без `?v=`», `bundle.js` собирается и сверяется с `deploy-loader` хэшем,
    миграции из репозитория накатываются на пустую БД (docker `supabase/postgres`) и
    сравниваются с продом (`supabase db diff`). Это закрывает п.4 навсегда.
15. **Publisher-критерий качества данных**: отдельный тест, который для каждой базы проверяет
    «ключ → вопрос → число вариантов» и **сверяет репозиторные ключи с продом** (у вас уже есть
    тест полноты, но нет теста на «ключ изменили, а версию файла и облако — забыли»).

### 3.4 На потом (продуктовые)

16. **Разбор «почему я ошибся»**: сейчас показывается ключ и пометка. Есть `explanation` в
    гистологии и теория по 72 темам — их можно подтянуть к вопросам анатомии по темам
    (`TOPICS` уже есть), и в разборе показывать ссылку на соответствующую тему теории.
    Это самая ценная учебная функция, которой не хватает: «ошибся → вот параграф → повтор».
17. **Интервальные повторения** (SM-2/FSRS) вместо «освоен при streak ≥ 2». Данные уже
    собираются (`attempts/correct/streak/last`), нужен только планировщик и экран «На сегодня».
18. **Экзамены для остальных баз**: 10 из 11 баз не имеют экзамена (`examAvailable: false`).
    Схема экзамена первого коллоквиума уже обобщена (`EXAM_SECTIONS`), для остальных нужны
    квоты по темам — это данные, а не код.
19. **Мобильный PWA-манифест** (иконки, `standalone`, `theme-color`) — 10 минут, сильно улучшает
    ощущение от Mini App.
20. **Экспорт только оформлений → полный импорт прогресса.** Сейчас README честно говорит, что
    полного восстановления нет; экспорт уже содержит всё нужное (`S.capture`), нужен обратный путь
    через `S.apply` с подтверждением и бэкапом.

## 6. Резюме в трёх пунктах

1. **Код и модель безопасности крепче, чем инфраструктура вокруг него** — «руками» поддерживаются
   версии файлов, миграции и деплой бандла, и именно там сейчас все хрупкие места.
2. **Главный технический долг — вес старта**: одна база из одиннадцати, а грузятся все;
   ленивая загрузка даёт самый большой выигрыш за наименьшие усилия.
3. **Главный продуктовый пробел — связка «ошибся → объяснение»**: контент для этого уже есть
   (теория, `explanation` в гистологии), но в тренажёре анатомии он не подключается.
